# 04 · 规则与口径

这份文件讲 `config/report_rules.yaml` 怎么用。
它是本项目的核心资产 —— 程序可以重写，口径和规则丢了就得重新问一遍财务。

## 理念：规则是数据，不是代码

财务说「含税收入必须等于不含税加税额」，这句话在系统里长这样：

```yaml
- id: CON-001
  name: 含税收入 = 不含税收入 + 税额
  type: reconcile
  table: stg_pms_revenue
  expression: "amount_with_tax"
  equals: "amount_net + tax_amount"
  tolerance_from: config/settings.yaml#run.amount_tolerance
  severity: block
  reason: 价税分离不平，财务无法入账
```

校验引擎把它编译成：

```sql
SELECT count(*), COALESCE(SUM(ABS((amount_with_tax) - (amount_net + tax_amount))), 0)
FROM stg_pms_revenue
WHERE ABS((amount_with_tax) - (amount_net + tax_amount)) > 0.01
```

好处是口径变更是**改配置文件**，不是改程序：能 diff、能 code review、能回滚，
新业务上线不用等排期。

## 一条规则的字段

### 通用字段（每类规则都要）

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | ✔ | 规则编号，出现在所有日志和报告里，别随意改 |
| `name` | ✔ | 人话名称，显示在待复核清单里 |
| `type` | ✔ | 8 类之一，决定判定逻辑 |
| `table` | ✔ | 查哪张表。既可以是 `stg_*` 也可以是 `mart_*` |
| `severity` | ✔ | `block`（阻断交付）/ `warn`（提示，可带例外放行） |
| `reason` | ✔ | 为什么要有这条规则。人来复核时看的就是这句话 |
| `where` | | 作用域，见下文 |

### `block` 还是 `warn` 怎么定

判断标准是「**错了会导致报表数字错，还是只是需要人确认一下**」。

- `block`：报表会算错，发出去就是错的
  （字段缺失会少计收入、勾稽不平无法入账、主键重复会翻倍、数据是旧的）
- `warn`：数字可能没错，但需要人看一眼
  （环比突变、佣金高于房费、人工导出与系统对不上）

`block` 项未清零时 `approve` 会被拒绝，所以不要往 `block` 上堆太多 ——
如果每天都有十几条阻断项过不去，人就会开始想办法绕过它。

## `where` 作用域：让规则保持有效

这是最容易被忽略、但决定规则能不能长期活下去的一个字段。

反面例子：`CMP-003` 检查渠道到数是否齐。

```yaml
# ❌ 没有作用域：扫全表，任何一天缺渠道都会命中
where: (无)
```

结果是：某个历史日期少导过一个渠道，这条 `block` 级规则就永远亮红灯。
过两周大家对它免疫了，然后在真的漏导那天也没人看。

正确写法是限定到「真正要发的那一期」：

```yaml
where: "source_key = 'ota' AND biz_date = (SELECT max(biz_date) FROM stg_channel)"
```

同理，`CON-002` / `CON-003` 检查佣金与结算的勾稽，这两列只对 OTA 有意义，
新媒体侧恒为 0，所以必须限定：

```yaml
where: "source_key = 'ota'"
```

不加这个，新媒体那些行会被「0 = 房费」这种伪命题判成不平，天天误报。

**原则：一条规则如果会在正常情况下长期报警，它就已经死了。**

## 八类规则

### `not_null` — 字段不得为空

```yaml
type: not_null
table: stg_pms_revenue
columns: [item, amount_with_tax, amount_net, tax_amount]
```

判定：`WHERE c1 IS NULL OR c2 IS NULL ...`
输出：命中的行数、涉及的列

### `completeness` — 到数数量不得低于应有数量

```yaml
type: completeness
table: stg_channel
column: channel
expected_from: config/data_sources.yaml#sources[ota].expected_accounts
min_ratio: 1.0
```

判定：`count(DISTINCT column)` 与 `ceil(expected * min_ratio)` 比较。
`expected_from` 用 `文件#路径` 语法引用别处的配置
（支持 `sources[ota]` 这种按键取值），阈值只写一遍。

### `date_freshness` — 数据必须新鲜

```yaml
type: date_freshness
table: stg_pms_revenue
column: biz_date
max_lag_days: 1
```

判定：`max(column)` 距今天的天数。
**这条是专治「静默失败」的**：管道没报错、报表正常生成、
但跑的是三天前的旧数据 —— 这是最危险的一类故障，
因为它看起来一切正常。宁可误报，也要留着。

### `reconcile` — 勾稽关系必须平

```yaml
type: reconcile
table: stg_pms_revenue
expression: "amount_with_tax"
equals: "amount_net + tax_amount"
op: "="                       # 可省略，默认 =
tolerance_from: config/settings.yaml#run.amount_tolerance
```

支持 `op`: `=` / `<=` / `>=` / `<` / `>`。
容差优先取 `tolerance_from`（跨文件引用），其次 `tolerance`，最后默认全局值。

各运算符的「不平」判定：

| op | 判定条件 |
| --- | --- |
| `=` | `ABS(A - B) > tol` |
| `<=` | `A > B + tol` |
| `>=` | `A < B - tol` |
| `<` | `A >= B` |
| `>` | `A <= B` |

### `non_negative` — 数值不得为负

```yaml
type: non_negative
table: stg_pms_revenue
columns: [amount_with_tax, amount_net, tax_amount]
allow_negative_items: [冲减, 退款]
```

判定：`WHERE c1 < 0 OR c2 < 0`，再排除白名单科目。
`allow_negative_items` 依赖表里有 `item` 列，没有就自动忽略这条白名单。

冲减和退款本来就该是负数，所以必须有白名单 ——
但白名单要写得窄，只列真正允许为负的科目。

### `deviation` — 环比不得突变

```yaml
type: deviation
table: mart_finance_daily
value_column: revenue_net
key_column: biz_date
pct_from: config/settings.yaml#run.deviation_pct
```

两种粒度，靠有没有 `required_columns` 区分：

**不带 `required_columns`**：`key_column` 本身就是期次。
按它分组求和，然后比较排序后的相邻两条。

```yaml
table: mart_finance_daily       # 每天比前一天的收入
key_column: biz_date
```

**带 `required_columns`**：`key_column` 是实体，`required_columns` 是期次。
同一实体跨期比，不同实体之间不会互相比。

```yaml
table: mart_ota_weekly          # 同一渠道比上一周
key_column: channel
required_columns: [week_start]
```

> 这个分支曾经写错过：两种粒度共用了「同一个 key 的上一期」这一套逻辑，
> 结果不带 `required_columns` 的规则永远不触发（每天只有一个 key，永远找不到「上一期」）。
> 整改后 DEV-001 才真正生效 —— 这也是为什么每条新规则上线后都要
> **故意造一次脏数据验证它会响**。

`prev == 0` 时跳过（从 0 涨到 X 的百分比没有意义）。

### `duplicate` — 主键不得重复

```yaml
type: duplicate
table: mart_finance_daily
keys: [biz_date, dept]
```

判定：`GROUP BY keys HAVING count(*) > 1` 的组数。
重复行会让收入翻倍，是后果最严重的一类错误，所以是 `block`。

### `cross_check` — 两表之间口径必须一致

```yaml
type: cross_check
left_table: stg_manual_finance
left_keys: [biz_date, dept]
left_value: amount_net
right_table: stg_pms_revenue
right_keys: [biz_date, dept]
right_value: amount_net
```

判定：两表各自按键汇总后 FULL OUTER JOIN，比较差异。

这条规则是给「人工导出 + 系统」并存的过渡期用的：
财务手工导出的部门收入，和 PMS 明细汇总出来的部门收入，必须对得上。
对不上就说明其中一方漏导、口径串行或范围不同 ——
这正是过渡期最该盯的地方。等上游接口接通、人工导出退役，这条规则就可以删了。

## 异常解释文案

规则只负责判定，文案单独配：

```yaml
anomaly_explain:
  not_null: "字段缺失：{columns} 在 {rows} 行上为空，疑似上游导出不全。"
  reconcile: "勾稽不平：{expression} 与 {equals} 差异合计 {diff} 元，共 {rows} 行。"
  ...
  default: "触发规则 {rule_id}：{reason}"
```

`{...}` 里的键由各检查函数填进 `detail` 字典。
如果某类规则没配模板，会退回 `default` 用 `reason` 兜底，不会崩。

在这个模板上花的功夫，直接决定财务愿不愿意看这份清单。
「勾稽不平：差异合计 500.0 元，共 1 行」比「CON-001 失败」有用得多。

## 报表口径

`report_rules.yaml` 上半部分的 `marts` 定义交付内容：

```yaml
marts:
  finance_daily:
    title: 财务日报
    cadence: daily              # 决定归到日报还是周报消息里
    sheets: 3
    owner: 财务
    sql: sql/marts/mart_finance_daily.sql
    validation_table: mart_finance_daily     # 校验挂在哪张表上
    outputs:
      - name: 收入汇总表
        table: mart_finance_revenue
        file: finance_revenue_daily.csv
        order_by: biz_date DESC
```

`outputs[].table` 是 DuckDB 里的表名，`file` 是导出文件名，`order_by` 保证输出确定性
（重跑 sha256 不变，审批指纹才不会莫名其妙失效）。

## 怎么新增一条规则

以「房态出租率不得高于 100%」为例：

1. 确认数据在：`stg_pms_room` 有 `occupancy_pct` 列
2. 在 `report_rules.yaml` 的 `validation` 下追加：

```yaml
  - id: RNG-003
    name: 出租率不得超过 100%
    type: reconcile
    table: stg_pms_room
    expression: "occupancy_pct"
    equals: "100"
    op: "<="
    severity: block
    reason: 出租率超过 100% 说明可供房或已售房数量导错
```

3. 跑 `python run.py selftest`（它会检查类型是否都有实现）
4. 跑 `python run.py check`，确认干净数据下这条规则**通过**
5. **故意造一次违反条件的数据，确认它会响** —— 这一步不能省
6. 提交时在 commit message 里写清是谁提的口径

## 口径变更流程

规则也是代码，改动要留痕：

1. 财务提出口径变更（最好带上真实数据样例）
2. 改 `config/report_rules.yaml`
3. `python run.py pipeline` 看变更后的判定结果
4. 如果变更会让历史数据大面积报警，先把 `severity` 降成 `warn` 观察一段时间
5. 提交，commit message 写清「谁提的、为什么改」
6. 用真实数据跑一轮完整交付，确认财务认可

`data/logs/manifest_YYYY-MM-DD.json` 里记录了每次运行用的规则判定结果，
口径变更前后可以直接对比 —— 这也是为什么会把运行清单落盘而不是只打日志。
