# 03 · 架构设计

## 技术选型与理由

### 为什么只有一个计算引擎（DuckDB）

日报的量级是每天几百行明细，周报按周聚合。这个规模下：

- Spark 的调度开销（几十秒级）远大于计算本身（毫秒级）
- 起一个集群来算 252 行，是纯粹的成本

DuckDB 是进程内的列存分析引擎，直接读 CSV / Parquet，
一个文件、一个进程跑完清洗 + 计算 + 校验 + 成表。
运维成本几乎为零，本地就能调试，出问题不用连集群。

代价是它不适合超大规模数据。真到那个量级，
`db.Warehouse` 是唯一需要替换的模块，上层 SQL 大部分能直接搬到 Spark SQL / Trino。

### 为什么先 Parquet、Iceberg 后置

`settings.yaml` 里有这么一段：

```yaml
lakehouse:
  backend: parquet          # parquet | iceberg
```

Iceberg 的价值在于多引擎共享表、时间旅行、schema 演进。
但本项目的写入方和读取方是同一个进程，单机单机——
先上 Iceberg 只是给自己加了一层依赖（`pyiceberg` 需要额外的 catalog 服务或 SQLite catalog）。

所以先跑 Parquet（DuckDB 原生支持，零依赖），把
`load.persist_staging` / `snapshot_table` 的产出约定定死。
将来要换 Iceberg，只改这几个函数内部，调用方和 SQL 都不用动。

`requirements.txt` 里已经把 `pyiceberg[sql-sqlite]` 注释好了，装上就能切。

### 为什么规则是 YAML 不是代码

如果用 Python 写校验，财务提一个口径变更就是一次「提需求 → 排期 → 改代码 → 发版」。
写成 YAML 之后：

- 口径变更是**改配置文件**，能 diff、能 review、能回滚
- 规则可以逐条测试（每条规则就是一个 SQL 片段）
- 新业务上线不用改程序，加几段 YAML
- 规则的能力边界由引擎决定，不会因为某个人写的临时 Python 逻辑而失控

这是简报里「不替财务拍板，它把规则变成可执行流程」的直接落地。
详见 [04-规则与口径.md](04-规则与口径.md)。

### 为什么 requests 延迟导入

```python
def push_wecom(cfg, content, *, dry_run=None):
    ...
    if dry_run:
        return {"dry_run": True, ...}
    import requests      # 延迟导入：dry-run 场景不需要这个依赖
```

dry-run 是默认路径。如果 `requests` 装在顶层，没装这个包的人连
`run.py status` 都跑不起来。把依赖放在真正用到它的分支里，
让「不联网也能跑完整条管道」成立。

## 模块依赖方向

```
                    __main__.py  (CLI)
                         │
                    pipeline.py  (编排)
                         │
     ┌───────┬───────┬───┴───┬───────┬────────┐
  extract  transform  load  report  review  deliver
     └───────┴───────┴───┬───┴───────┴────────┘
                         │
              config.py · audit.py · db.py        ← 基础设施
                         │
                    rules/engine.py               ← 被 report 与 check 共用
```

依赖是单向的：上层依赖下层，基础设施不反向依赖任何业务层。
`rules/engine.py` 只依赖 `config` 和 `db`，不知道报表长什么样，
所以规则既能查 `stg_*` 也能查 `mart_*`。

## 三层硬约束的实现位置

简报的落地原则有四条，其中三条在代码里有明确落点：

| 原则 | 实现位置 | 表现 |
| --- | --- | --- |
| 原始数据只读 | `db.guard_raw()` | 往 `data/raw/` 写文件直接抛 `RawLayerWriteBlocked` |
| 凭证与日志留痕 | `audit.Auditor` | 每个动作一行 JSONL；审批凭证记录报表 sha256 |
| 权限按角色隔离 | `audit.Auditor.check()` | 每个阶段动工前过闸门，越权抛 `PermissionDenied` |
| 异常必须复核 | `review.gate.approve(require_clean=True)` | 有阻断项时拒绝签字 |

四条里最容易被做成「文档里的承诺」的是后两条。这里都做成了**代码执行路径上的必经点**：
`stage_build` 第一行就是 `auditor.check("build")`，绕不过去。

## 审批凭证怎么绑住制品

问题：财务下午 3 点签了字，下午 4 点有人手工改了 CSV，然后点交付。怎么防？

```
approve 时：sha256(finance_revenue_daily.csv) = 476b3c31aa89a2f4  → 写进 approval_*.json

deliver 时：现场重算磁盘上文件的 sha256
            476b3c31aa89a2f4 ≠ 7e807f366407a5ed  → 拒绝交付
```

**关键点是「现场重算」**。一开始实现成拿 `artifacts_*.json` 里记录的旧哈希去比对，
那是自己和自己对答案，永远发现不了篡改 —— 这个 bug 在实测中被抓出来了，
现在 `deliver/wecom.py` 里明确注释了这一点。

同时它也允许「内容一致的重跑」：因为 CSV 输出是确定性的，
重跑 `build` 得到的文件字节完全相同，sha256 一样，交付照常通过。

## 扩展点

### 换 Iceberg

```yaml
lakehouse:
  backend: iceberg
  iceberg:
    warehouse: data/lakehouse
    catalog_uri: sqlite:///data/lakehouse/catalog.db
    namespace: hotel
```

改 `load/writer.py` 里 `snapshot_table()` 的实现，把 `COPY ... TO parquet`
换成 PyIceberg 的 `append`。调用方不用动。

### 接自动取数

`extract/loader.py` 的 `load_raw_views()` 目前是「登记 CSV 视图」。
接真系统时换成直连查询即可，只要产出的表名仍是 `raw_<table>`，
`sql/staging/*.sql` 及之后的全部环节一行都不用改。

`config/data_sources.yaml` 里的 `mode: auto` / `mode: manual`
就是为这个切换预留的标记。

### 多酒店

当前 `settings.project.hotel` 是单店。要扩多店：

1. 原始层按店分目录：`data/raw/<店key>/...`
2. 清洗层和报表层加一个 `hotel_key` 维度列
3. 校验规则的 `where` 作用域按店加条件
4. `report.current_biz_date` 改成按店取

这是真正需要改代码的一次演进，不是改配置能覆盖的。

### 新的规则类型

比如「字段取值必须在白名单内」：
在 `rules/engine.py` 加一个 `_check_enum()` 并注册进 `CHECKS` 字典，
再在 `report_rules.yaml` 里用 `type: enum` 引用。
`selftest` 会检查每种声明的 `type` 是否都有实现，漏了会直接报出来。

## 已知边界

**没做的**：

- 增量更新。当前是全量重算，数据量大了要改成按日期分区增量
- 调度。没内置 cron / Airflow，靠外部调度器调 `run.py pipeline`
- 并发写。DuckDB 单写多读，多个人同时 `build` 会锁
- 数据校验的「例外登记」机制。现在只能改规则或修数据，没有「这条已知例外、放行」的记录

**刻意不做的**：

- 自动改数。系统只报告问题，不替人修数据
- 自动审批。`severity: warn` 的项也不自动放行，必须人签字
- 在原始层做任何加工
