# 02 · 数据流与分层

## 六层职责

| 层 | 位置 | 谁写 | 能改吗 | 职责 |
| --- | --- | --- | --- | --- |
| 原始层 | `data/raw/` | 上游 / `mock` | **只读**，中台不许回写 | 原样保存上游给的 CSV，一行不改 |
| 清洗层 | DuckDB 里的 `stg_*` 表 | `transform` | 可重跑 | 统一列名、`TRY_CAST` 纠正类型 |
| 落地层 | `data/lakehouse/` | `load` | 覆盖写 | Parquet 快照，可换 Iceberg |
| 报表层 | DuckDB 里的 `mart_*` 表 + `data/marts/*.csv` | `build` | 覆盖写 | 按口径聚合，导出交付文件 |
| 闸门层 | `data/review/` | `check` / `approve` | 追加 + 覆盖 | 校验结果、待复核清单、审批凭证 |
| 交付层 | `data/outbox/` | `deliver` | 覆盖写 | 微盘同步目录 + 企微通知载荷 |
| 痕迹层 | `data/logs/` | 全程 | 只追加 | 审计 JSONL + 运行清单 |

## 为什么原始层必须只读

简报的落地原则第一条就是「原始数据只读」。它在代码里的实现是 `db.guard_raw()`：

```python
with Warehouse(cfg) as wh:
    wh.to_parquet(sql, cfg.path("raw") / "x.parquet")
    # RawLayerWriteBlocked: 禁止写入原始层：...
```

任何试图把加工结果写进 `data/raw/` 的调用都会被直接拦下。
目的很实际：**出问题时能回到原点**。只要原始层没被动过，
所有下游结果都能重算出来；一旦有人「顺手修一下原始数据」，
就再也说不清到底是数据错了还是加工错了。

唯一的例外是 `mock` 生成器 —— 它扮演的是「上游系统」，
上游本来就在生产原始数据，所以它写 `raw` 不经过这个守门员。

### mock 的文件清理策略

原始层原则上「只增不删」，但按日期命名的导出文件如果不清理，
换个时间窗重跑时旧日期文件还会被 `raw_*` 视图的 glob 读进来 ——
这正是简报里最怕的「旧数据静默混入」。

做法：**先按窗口全部覆盖重写，写完之后才删「本次窗口之外」的旧文件**
（`mock._remove_stale`）。只认自己生成的 `<业务>_<YYYYMMDD>.csv` 命名，
日期解析不出来的文件一律不碰，避免误删手工放进来的数据。

好处：稳态重跑删除量为 0；窗口整体平移一天时才删 5 个。
而且万一半路失败，原始层绝不会被清空。

## 字段血缘：每个数字都能反查到来源文件

原始视图是用 `read_csv_auto(..., filename=true)` 登记的，所以每张 `raw_*` 视图
都带一列 `filename`。清洗层把它接成 `src_file`：

```sql
CREATE OR REPLACE TABLE stg_pms_revenue AS
SELECT
    TRY_CAST(NULLIF(TRIM(biz_date), '') AS DATE) AS biz_date,
    ...
    NULLIF(TRIM(filename), '')                   AS src_file
FROM raw_pms_revenue;
```

于是出现异常时可以直接问「这个数是哪个文件来的」：

```sql
SELECT DISTINCT src_file FROM stg_pms_revenue WHERE item IS NULL;
```

## 为什么清洗层不做过滤

一个很容易犯的错：在清洗 SQL 里加 `WHERE item IS NOT NULL AND amount_net >= 0`，
把「脏」行 drop 掉。

**那样校验规则就永远发现不了空值和负数了** —— 数据在到达规则层之前已经被清理干净，
所有规则都变成永远通过的摆设，「异常必须复核」也就无从谈起。

所以分工会这么定：

- **清洗层**：只做机械转换（列名统一、类型转换、去首尾空格），**一行不删**
- **规则层**：负责判定「这份数据能不能用」

代价是 marts 里可能包含脏数据算出来的数字。这是有意接受的：
报表先生成出来、同时标出异常、等人确认，比「报表生成失败、什么都没有」更好用。
真要阻断，规则里的 `severity: block` 会拦住交付。

## 命名约定

| 对象 | 约定 | 例子 |
| --- | --- | --- |
| 原始文件 | `<业务>_<YYYYMMDD>.csv` | `revenue_20260921.csv`、`channel_20260921.csv` |
| 原始视图 | `raw_<来源表>` | `raw_pms_revenue` |
| 清洗表 | `stg_<来源表>` | `stg_pms_revenue` |
| 报表表 | `mart_<主题>` | `mart_finance_daily`、`mart_ota_weekly` |
| 交付文件 | 见 `report_rules.yaml → outputs[].file` | `finance_revenue_daily.csv` |
| 内部视图 | 前缀下划线 | `_week_bounds`（已废弃，改用 `mart_week_bounds`） |

原始文件按天切分（一天一个文件），是因为上游本来就是按天导出；
按天切还有个好处：某天数据有问题时可以只替换那一个文件重跑。

## 中间表与交付物的关系

以财务日报为例，一个 `sql/marts/mart_finance_daily.sql` 产出 4 张表：

```
stg_pms_revenue  (科目级明细，252 行)
      │
      ▼  GROUP BY biz_date, dept
mart_finance_daily        ← 校验基表（UNQ-001 / DEV-001 挂在它上面）
      │
      ├── mart_finance_revenue   收入汇总表   按天，全部门合计
      ├── mart_finance_tax       税额明细表   按天 + 部门
      └── mart_finance_dept      部门收入表   按部门，期间累计
```

**为什么留一张「校验基表」？** 因为规则需要一个稳定、粒度明确的落点。
如果规则直接挂在交付表上，那表结构一改（比如为了报表好看加了一列），规则就废了。
放在 `mart_finance_daily` 上，交付表怎么改版都不影响校验。

## 周报为什么只出「完整周」

`sql/marts/mart_weekly.sql` 里有一句看起来多余的条件：

```sql
WHERE week_start >= (SELECT min_date FROM mart_week_bounds)
  AND week_start + 6 <= (SELECT max_date FROM mart_week_bounds)
```

它把「残周」排除在周报之外。原因很实在：

数据从月中开始，或者本周才跑了 1 天，都会形成残周。
拿 6 天的残周去和 7 天的完整周比环比，会算出 **-85%** 这种纯属噪音的「偏离」，
而真正的问题会被这种假报警淹掉。

这个坑在第 14 天数据上实测踩到过：`DEV-002` 报 booking 间夜数 -85.75%，
全是噪音。加上这个过滤之后，`mock_days` 也从 14 调到 28
（至少跨 3 个自然周才凑得出 2 个完整周做环比）。

## 时间口径

- 业务时区固定 `Asia/Shanghai`（`audit.TZ`），所有时间戳都带 `+08:00`
- 日粒度：`biz_date`，来自上游导出
- 周粒度：`week_start = date_trunc('week', biz_date)`，即**该周周一**
- 本期业务日期：`max(biz_date)`，作为整个交付批次的编号（`report.current_biz_date`）

## 幂等性

所有表都是 `CREATE OR REPLACE TABLE`，所有产物都是覆盖写。
同一天重跑 N 次，结果完全一致，不会累加、不会重复。

交付文件的内容也是确定性的（CSV 带 `ORDER BY`，Parquet 同理），
所以重跑后 sha256 不变 —— 这也是为什么审批后重跑 `build` 能让指纹自动恢复。
